# チケットを書く・直すとき

## 上位の文書は触らない

- `docs/tickets/00-api-map.md`（モジュール横断の名前の契約）と `docs/PLAN.md`（= `tmp/witty-gliding-clover.md`）は、**チケットの都合で編集しない**
- 必要な変更はチケット末尾の **§「API 地図への変更提案」** に書いて利用者に上げる
- 優先順位は **PLAN ＞ 00-api-map ＞ 各チケット**

## 形（10 節をこの順に）

1. ヘッダ（`| 項目 | 値 |` の表。ID・題・Phase・前提・見積もり）
2. 目的（1〜3 行）
3. 参照（PLAN の節、`voicedock@d3d595e` の `file:line`）
4. 作るもの（`| パス | 内容 |` の表）
5. 仕様（宣言＝ Swift のコード・番号付きの手順・定数・文言の逐語・エラーの写し方・ログ）
6. テスト（テストファイルごとに `| 関数名 | 表示名 | 準備 | 期待 |`）
7. 破壊による証明（`| 壊し方 | 落ちるべきテスト |`）
8. 受け入れ条件（`- [ ]` のチェックリスト）
9. SPEC の変更（無ければ「なし」）
10. マージ後にやること（無ければ「なし」）

例外: 文書のチケット（T-35・T-42・T-43・T-44）は 5「仕様」の代わりに書式・シナリオ・文書テストの節を持つ。

## 書式

- **GFM の表の中ではコードスパン内の `|` も `\|` にエスケープする**（機械検査の 1 番目が列数を数えている）
- 「作るもの」のパスは **1 チケットにつき 1 人だけ**が持つ（検査 6。並列実装が衝突しないための契約）
- 規範 ID（CV / ND / RV / DR / PT / CR / PR）は仕様に定義があるものだけを使う（検査 5）
- `PLAN §x.y` の参照は実在する節を指すこと（検査 4）

## 直したら毎回回す

```bash
python3 docs/porting-notes/check-tickets.py
```

**0 件**であること。10 の検査（表の列数 / 目次とファイルの対応 / チケット間の参照 / `PLAN §` の節 / 規範 ID / 作るものの重複 / PT-11 の語 / F-54 で消したキー / 地図の未使用の型 / 10 節の形）を見る。
