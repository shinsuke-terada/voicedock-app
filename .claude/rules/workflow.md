# 進め方（1 チケット = 1 issue = 1 PR）

## 文書の優先順位と、食い違いの判断

**PLAN ＞ 00-api-map ＞ 各チケット。** 食い違いを見つけたら:

1. **実装を止める。**食い違ったまま先へ進まない
2. 上位の文書に合わせる（チケットが間違っていれば、チケットを直す）
3. 直すのは**同じ PR の中**。実装と文書の修正を分けない
4. `00-api-map.md` と PLAN は**チケットの都合で編集しない**。必要な変更はチケット末尾の §「API 地図への変更提案」に書いて利用者に上げる
5. どちらが正しいか判断できないときは、推測で進めずに**利用者に聞く**

## T-01（ブートストラップ。いまはここ）

git リポジトリがまだ無いので、下の「T-02 以降」の 1〜2 は T-01 には適用できない。T-01 は `T-01-repository-skeleton.md` §1 の手順そのままに進める。

`git init -b main` → ドキュメントだけの最初のコミット → `git branch develop` → `gh repo create`（**外部への公開なので利用者の確認を得てから**）→ `git switch -c feat/T-01-repository-skeleton develop` → 残りのファイル → `make lint && make test` → PR。

## T-02 以降

1. チケットの「前提」のチケットがすべて `develop` にマージ済みであることを確かめる
2. `develop` から `feat/T-nn-<短い英語名>` を切る
3. チケットの「作るもの」を**上から順に**作る。**チケットに書いていない公開 API を足さない**
4. 「テスト」の節のテストを**全部**書き、`make lint && make test` が通ることを確かめる
5. 「破壊による証明」を 1 項目ずつ行う（`/prove-by-breaking`）
6. `ticket-review` エージェントに差分を見せ、Critical が無いことを確かめる
7. PR を出す。本文の書き方は `/implement-ticket` スキルにある
8. **マージは利用者が行う。**issue は手で閉じる

## 並列で走らせるとき

- 同時に走らせるのは**最大 4 本**（8 本で使用量の上限に当たった）
- **「作るもの」のパスが重なるチケットを同時に走らせない。**パスの持ち主は 1 チケットに 1 人だけ（`check-tickets.py` の検査 6）
- 前提が満たされていないチケットを先回りして実装しない
- 選び方と投げ方は `/next-tickets`

## 文脈の使い方

- `docs/PLAN.md`（T-01 より前は `tmp/witty-gliding-clover.md`）は 3,100 行ある。**全文を読まない。**`grep -n` で節を探し `Read` の offset/limit で必要な範囲だけ読む
- チケットが §「参照」で指している PLAN の節・API 地図の行・`voicedock@d3d595e` の `file:line` は `ticket-brief` エージェントに逐語で引かせる
- 同じファイルを何度も全文読みしない
