# 次に着手できるチケットを選んで走らせる

## 1. 現在地

```bash
cat docs/tickets/STATUS.md
git log --oneline -20 2>/dev/null || echo "git はまだ無い（T-01 の前）"
git branch -a 2>/dev/null
```

`docs/tickets/README.md` の「一覧（依存順）」の表が、各チケットの Phase と「前提」を持っている。

## 2. 候補を出す

**前提のチケットがすべて `develop` にマージ済み**のものだけが候補。前提が 1 つでも欠けていたら候補にしない。先回りして実装しない。

Phase 0（P0）は候補に入れない。実機なので `/poc-measure` に回す。

## 3. 重なりを確かめる（並列の条件）

候補を 2 本以上同時に走らせる前に、**各チケットの §「作るもの」の表のパスが 1 つも重ならないこと**を確かめる。

```bash
for t in T-06 T-07 T-25; do
  echo "== $t"
  sed -n '/^## 3\. 作るもの/,/^## 4\./p' docs/tickets/$t-*.md | grep -oE '`(Sources|Tests|tools|scripts|Vendor|docs)/[^`]+`'
done | sort | uniq -d
```

重複が出たら、そのチケットは**同時に走らせない**（`check-tickets.py` の検査 6 が「パスの持ち主は 1 チケットに 1 人」を保証しているので、正しく分かれていれば重複は出ない。出たら先にチケット側の問題）。

さらに次も確かめる:

- `Package.swift` を触るのは T-01 だけ。T-01 は単独で走らせる
- `docs/SPEC.md` を触るチケット（T-05 とその後の §「SPEC の変更」がある回）は同時に走らせない
- `00-api-map.md` への変更提案が出そうなチケットは、提案が出た時点で止まるので、単独で走らせた方が早い

## 4. 投げる

**最大 4 本**（8 本で使用量の上限に当たった）。`ticket-implementer` を 1 つのメッセージで並列に起動する。

各エージェントへの指示に必ず入れるもの:

- 対象のチケット ID とファイルパス
- 「§『作るもの』の表にあるパス**以外**のファイルを一切触らないこと。ほかのチケットが並列で走っている」
- 「切るブランチは `feat/T-nn-<短い英語名>`。`develop` から」
- 「`/implement-ticket T-nn` の手順に従うこと」
- 「破壊による証明は**並列中はやらない**。全部の実装が終わってから 1 本ずつ行う」（`git checkout --` が他のブランチの作業を巻き込むため）

## 5. 戻ってきたら

1 本ずつ:

1. `ticket-review` エージェントに差分を見せる
2. Critical が残っていれば実装エージェントに差し戻す
3. `/prove-by-breaking T-nn`（ここで初めて。1 本ずつ、順番に）
4. PR を出す

**マージはしない。**利用者に一覧で上げる:

| チケット | ブランチ | `make lint`/`make test` | レビュー | 破壊による証明 | PR |
|---|---|---|---|---|---|
| T-nn | feat/… | 通った | Critical 0 | 3/3 | #12 |
