# チケット $ticket の実装

チケットは「**誰が実装しても同じソースコードになる**」水準で書いてある。だから創意工夫は要らない。要るのは、**書いてあるとおりに全部作ること**と、**書いていないものを足さないこと**の 2 つだけ。

## 0. 先に読むもの

1. `docs/tickets/$ticket-*.md` を**全文**。要約しない。定数・文言（日本語の逐語）・SQL・argv・ログのイベントとフィールドは、そこに書いてある文字列がそのまま正解
2. **最初の Swift を書く前に** `.claude/rules/swift-code.md` と `.claude/rules/swift-tests.md` を読む。`paths` 付きのルールは既存ファイルを読んだときに読み込まれるので、新規ファイルを作る流れでは発火しない
3. チケット §「参照」が指す PLAN の節・`00-api-map.md` の行・`voicedock@d3d595e` の `file:line` は `ticket-brief` エージェントに**逐語で**引かせる（自分で PLAN を全文読まない）

## 1. 前提の確認

**T-01 のときはここを飛ばして** `.claude/rules/workflow.md` の「T-01（ブートストラップ）」に従う。まだ git リポジトリが無い。

T-02 以降:

```bash
git branch --list                      # 前提のチケットが develop にマージ済みか
git switch develop && git pull
git switch -c feat/$ticket-<短い英語名>
```

前提が揃っていなければ**そこで止めて報告する**。先回りして前提のチケットを実装しない。

## 2. 作る

チケット §「作るもの」の表を上から順に。表にあるパスだけを作り、**表に無いファイルを触らない**（並列で別のチケットが走っている可能性がある。パスの持ち主は 1 チケットに 1 人だけ）。

- `Package.swift` は T-01 が 11 ライブラリ + 2 実行ファイル + 16 テストターゲットを全部入りで作る。**T-01 以外は触らない**
- **チケットに書いていない公開 API を足さない。**足す必要が出たら止めて、`00-api-map.md` とチケットを先に直す（`.claude/rules/workflow.md` の判断木）
- 型・関数の名前は `00-api-map.md` と先行チケットから取る

## 3. テストを書く

チケット §「テスト」の表の行を**全部**。1 行 1 テスト。関数名・表示名・準備・期待が表に書いてある。

- 表示名は日本語。規範 ID（CV / ND / RV / DR / PT / CR / PR）に対応するテストは表示名を ID で始める
- **期待値を実装から作らない**（TEST-01）。仕様の表と固定値から書く
- 空の入力のテストを 1 本入れる（TEST-28）

## 4. 通す

```bash
make lint && make test
```

`make lint` が通らない PR は出さない。警告はエラーになる（`treatAllWarnings(as: .error)`）。

## 5. 破壊による証明

`/prove-by-breaking $ticket`。チケット §「破壊による証明」の表を 1 項目ずつ。落ちたテスト名を記録する。

## 6. レビュー

`ticket-review` エージェントに差分を見せる。Critical が残っていたら直してからやり直す。

## 7. 受け入れ条件

チケット §「受け入れ条件」のチェックリストを 1 つずつ確かめる。**確かめずにチェックを付けない。**

## 8. PR

```bash
gh pr create --base develop --title "$ticket <題>" --body "$(cat <<'EOF'
## 目的

<チケット §「目的」の 1〜3 行>

## 変更

<作ったファイルの一覧と、それぞれ何をするか。チケット §「作るもの」の表に対応させる>

## テスト

<make lint と make test の出力を貼る。テストの本数と、追加したテストの表示名>

## 破壊による証明

| 壊し方 | 落ちたテスト |
|---|---|
| <チケットの表の壊し方> | <実際に落ちたテストの表示名> |

## SPEC の変更

<docs/SPEC.md に足す・変える表。無ければ「なし」>

## マージ後にやること

<無ければ「なし」>
EOF
)"
```

**マージはしない。**利用者が確かめて `develop` にマージする。issue は手で閉じる。

## 途中で食い違いを見つけたら

止める。`.claude/rules/workflow.md` の判断木に従う。`00-api-map.md` と PLAN はチケットの都合で編集せず、チケット末尾の §「API 地図への変更提案」に書いて利用者に上げる。
